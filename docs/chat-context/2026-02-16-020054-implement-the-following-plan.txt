│                                                                              │
│ ASR Speed Optimization Plan                                                  │
│                                                                              │
│ Context                                                                      │
│                                                                              │
│ Whisper-tiny.en on ARM64 (OnePlus CPH2767) takes ~4 seconds to process 2     │
│ seconds of audio (0.5x real-time). The model is already INT8 quantized       │
│ (75MB) and the build uses -O3, LTO, NEON SIMD. We need to squeeze more speed │
│  from config/code changes without switching ASR engines.                     │
│                                                                              │
│ Key Findings                                                                 │
│                                                                              │
│ - Model ggml-tiny.en.bin is already INT8 quantized — no further model swap   │
│ available for tiny                                                           │
│ - speed_up param was removed from newer whisper.cpp — NOT available          │
│ - audio_ctx param IS available — controls mel spectrogram context window     │
│ (default ~1500 frames = 30 seconds). Reducing this is the biggest lever.     │
│ - Built-in VAD is available (vad, vad_model_path, whisper_vad_params) but    │
│ requires a separate model file                                               │
│ - Build flags are already optimal (-O3, -flto, -funroll-loops, NEON SIMD)    │
│                                                                              │
│ Changes (all in asr/asr_wrapper.cpp)                                         │
│                                                                              │
│ 1. Reduce audio_ctx to 512                                                   │
│                                                                              │
│ The default 1500 processes a 30-second mel window even for 2-second chunks.  │
│ Setting audio_ctx = 512 (~10 seconds) is more than enough for our 2-4 second │
│  chunks and significantly reduces attention computation.                     │
│ params.audio_ctx = 512;                                                      │
│                                                                              │
│ 2. Bump threads from 4 to 6                                                  │
│                                                                              │
│ OnePlus has 8 cores (4 big + 4 efficiency). Using 6 threads utilizes more    │
│ big cores without saturating.                                                │
│ params.n_threads = 6;                                                        │
│                                                                              │
│ 3. Simple amplitude-based VAD (pre-whisper)                                  │
│                                                                              │
│ Before calling whisper_full(), check if the audio chunk has speech. If peak  │
│ amplitude is below a threshold (e.g., 0.01), skip whisper entirely. This     │
│ avoids wasting 4 seconds on silence.                                         │
│ // Before whisper_full():                                                    │
│ float peak = 0;                                                              │
│ for (size_t i = 0; i < audio_buffer_.size(); i++) {                          │
│     float v = std::abs(audio_buffer_[i]);                                    │
│     if (v > peak) peak = v;                                                  │
│ }                                                                            │
│ if (peak < 0.01f) {                                                          │
│     audio_buffer_.clear();                                                   │
│     return partial_text_;  // Skip — silence                                 │
│ }                                                                            │
│                                                                              │
│ 4. Increase minimum chunk from 2s to 3s                                      │
│                                                                              │
│ Whisper has ~2 seconds of fixed overhead per run. Processing 3 seconds of    │
│ audio means fewer runs and better throughput. The user experiences slightly  │
│ more latency per sentence but overall fewer wasted whisper invocations.      │
│ const size_t chunk_samples = SAMPLE_RATE * 3;  // 3 seconds                  │
│                                                                              │
│ 5. Set max_tokens to cap decoding                                            │
│                                                                              │
│ Prevent whisper from generating excessively long output on noisy input. Cap  │
│ at 32 tokens per segment (plenty for 3-4 seconds of speech).                 │
│ params.max_tokens = 32;                                                      │
│                                                                              │
│ 6. Filter hallucinations before sending to MT                                │
│                                                                              │
│ Whisper-tiny commonly hallucinates patterns like "[MUSIC PLAYING]",          │
│ "(speaking in foreign language)", "you", "Thank you." on silence/noise.      │
│ Filter these out in process_chunk() before appending to confirmed_text_.     │
│                                                                              │
│ Files to Modify                                                              │
│                                                                              │
│ - asr/asr_wrapper.cpp — All 6 changes above (VAD, audio_ctx, threads, chunk  │
│ size, max_tokens, hallucination filter)                                      │
│                                                                              │
│ Expected Impact                                                              │
│                                                                              │
│ ┌────────────────────────┬─────────────────────────────────────┐             │
│ │         Change         │          Estimated Speedup          │             │
│ ├────────────────────────┼─────────────────────────────────────┤             │
│ │ audio_ctx 1500→512     │ 1.5-2x (less attention computation) │             │
│ ├────────────────────────┼─────────────────────────────────────┤             │
│ │ 6 threads              │ 1.1-1.3x                            │             │
│ ├────────────────────────┼─────────────────────────────────────┤             │
│ │ VAD skip silence       │ Saves 100% on silent chunks         │             │
│ ├────────────────────────┼─────────────────────────────────────┤             │
│ │ 3s chunks (fewer runs) │ ~1.3x throughput                    │             │
│ ├────────────────────────┼─────────────────────────────────────┤             │
│ │ max_tokens=32          │ Prevents runaway decoding           │             │
│ └────────────────────────┴─────────────────────────────────────┘             │
│                                                                              │

⏺ Great idea — let me think through this with you.

  What you're proposing

  Use Qwen not as a translator, but as a post-editor/verifier:
  - NMT gives you fast, reliable Hindi (~20-49ms)
  - Pass Qwen both the English source + NMT Hindi
  - Qwen checks contextual correctness and makes minimal corrections

  How this differs from what's already there

  The current speculative decoding (build_refinement_prompt()) is similar but
  subtly different — it asks Qwen to regenerate the full Hindi translation using
   NMT as a "draft". That's why it's slow (6.5s full-prefill) and often produces
   worse output than NMT, because Qwen3-0.6B isn't good enough at Hindi
  generation.

  Your idea is lighter: don't ask Qwen to translate, ask it to judge/fix.

  Three possible approaches

  A) Confidence scoring (no generation, fastest)
  - Tokenize the NMT Hindi output
  - Run ONE forward pass through Qwen with "English: {src}\nHindi: {nmt_hindi}"
  - Look at the logits/perplexity for each Hindi token
  - If confidence is high → accept NMT as-is (zero generation cost)
  - If confidence is low on specific tokens → flag them
  - This is essentially "how surprised is Qwen by this translation?"
  - Cost: one forward pass, no autoregressive loop

  B) Minimal correction prompt (light generation)
  - Prompt: "English: {src}\nHindi translation: {nmt_hindi}\nIf correct, reply 
  CORRECT. Otherwise reply with only the corrected Hindi:"
  - Most of the time Qwen says "CORRECT" (1 token) → fast
  - Occasionally it outputs a corrected version
  - Risk: Qwen3-0.6B may "correct" things that were already right

  C) Token-level verification (hybrid — what speculative decoding already does)
  - This is the existing 65% acceptance approach but reframed
  - Already implemented, just needs device enablement

  My recommendation

  Approach A (confidence scoring) is the strongest for your situation because:
  1. No generation — just one forward pass, same cost regardless of output
  length
  2. Qwen is better at judging than generating — small models can assess
  plausibility even when they can't produce good text
  3. NMT is already correct most of the time — you just need a safety net for
  edge cases
  4. Graceful fallback — if Qwen is uncertain, you still have the NMT output
  (which is good)

  The flow would be:
  English → NMT (49ms) → Hindi draft
                       → Qwen scores draft (one forward pass)
                       → confidence high? ship NMT as-is
                       → confidence low? flag it (or fall back to NMT anyway,
  since Qwen can't do better)

  The practical question is: given that Qwen3-0.6B can't generate good Hindi 
  anyway, what do you actually do when confidence is low? If the answer is
  "still use NMT", then the scoring becomes more of a quality metric/logging
  tool than a correction mechanism.

  Approach B is more actionable if you want actual corrections, but the 6.5s
  latency + Qwen's limited Hindi ability makes it risky.

  What's your thinking — do you want Qwen to actually correct the output, or
  more to score/validate it? And how important is keeping latency low (shipping
  NMT immediately vs. waiting for Qwen)?
